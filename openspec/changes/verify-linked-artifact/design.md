## Decisions

### 1. Two explicit local operations

Proposed public interface:

```text
assuredloop artifact capture --out ABS_NEW_DIRECTORY
  [--archive ABS_LOCAL_TGZ] [--dependency-root ABS_INSTALLATION_OWNER]
assuredloop artifact verify --record ABS_CAPTURE_JSON --integrity SHA512_SRI
  [--dependency-root ABS_INSTALLATION_OWNER]
```

Both operate on the package that owns the invoked executable. `--target` is deliberately absent: these commands do not initialize or assess a consumer's workflow. Resolve the actual package from the CLI module location/realpath, not cwd, a report-provided executable or an untrusted record's path. Tests may inject scoped fixture roots at a private module boundary; that is not a user-facing fallback.

`capture` creates a previously nonexistent output directory, writes `artifact.tgz`, `capture.json`, and an available `dependency-lock.json`. With `--archive`, copy that local archive's exact bytes; without it, run native local npm packaging with `--ignore-scripts --offline --workspaces=false`, explicit output/cache locations and no install or publication. The report identifies `supplied` versus `generated` origin. Generated bytes are a new artifact, never proof of a previously distributed tarball's SRI.

`verify` reads the bundle and expected SRI supplied on the command line. It hashes the actual retained archive, compares it with both that expectation and the capture descriptor, then compares current installed package contents and available dependency observations. Paths recorded as observations do not authorize reads; the bundle permits only its fixed relative data filenames, and a current dependency root is explicitly selected again. Output is fresh JSON on stdout, not a rewrite of the capture. A moved bundle is supported; a different current installation location is reported and compared by content, not silently treated as the old Git checkout.

Alternative rejected: make every `init` validate arbitrary directory bytes against an SRI. SRI identifies archive bytes, not a filesystem tree; existing initialization never required the archive. Retrofitting it would change compatibility and still not resolve the identity question correctly.

### 2. Archive identity and installed content are different checks

Use Node crypto for byte digests and native npm packing semantics for package membership, including npm's automatic README/package.json/bin inclusion and ignored files. Use the popular `tar` package as a direct, exactly pinned dependency for strict streaming archive inspection; do not use an undeclared npm-internal dependency or write a tar parser. Select and verify a compatible release older than 24 hours during implementation; retain its license and test the chosen API. This dependency choice is part of this proposed scope, not already installed.

Accept regular file members below `package/`, and harmless directory entries. Reject duplicate normalized file paths, absolute/traversing/backslash/control-character paths, symlinks, hardlinks, device entries and malformed/truncated archives. Inspect entries as data; do not extract an untrusted archive over the source or consumer. Apply explicit resource bounds with an `incomplete`/unsupported-limit result rather than a truncated PASS.

Record a stable sorted file inventory of normalized relative path, raw byte size, SHA-256 and executable-bit meaning. Compare complete membership and every member's bytes/executable meaning against the selected installation. Ignore archive timestamps, owner IDs and gzip metadata for this filesystem comparison; those remain covered by exact archive SRI. Never pretend content equality implies original-archive byte equality. Verify existing contract metadata and files separately with the delivered contract checker.

For a dirty source, the retained tarball is the reconstructible code/assets overlay. Retaining only Git HEAD or a patch hash is insufficient. The tool does not install or automatically apply this artifact. The owner can explicitly choose it, commit/rebuild the source, or select an independently obtained immutable archive.

### 3. Source provenance describes observed package content

If the selected package is itself a Git source root, record its full HEAD and available origin identity separately from contract `source_ref`; source origin text is not ownership authentication. Do not walk up from an installed `node_modules` package and use the consumer's HEAD. A package nested in an unsupported monorepo layout reports Git provenance unavailable rather than guessing.

Derive changed packaged paths from content/membership comparison with a native package inventory of the fixed HEAD, using an owned temporary Git export when necessary. This includes changed, added and deleted members, not merely `git status` matches. A source with only excluded changes can have dirty repository status but matching packaged content. If HEAD objects or source comparison cannot be obtained, report that coverage as unavailable; retained archive identity remains independently inspectable.

No archive is claimed to be a clean source build unless the complete packaged comparison supports it. Ignored but actually packaged files are still content. Neither `.gitignore` nor absence from `git diff` is a general exclusion rule for the artifact.

### 4. Dependency lock and identity checks have an explicit scope

`--dependency-root` names the npm installation owner whose root `package-lock.json` and installed tree are to be inspected. Without it, inspect only the selected package root for a supported source lock; otherwise report dependency coverage unavailable. Never search arbitrary ancestors or read a consumer lock merely because cwd happens to be there. Do not use `node_modules/.package-lock.json` as the captured source lock.

Before capturing a supported lock or deriving an expected tree, check the selected root for `npm-shrinkwrap.json`. npm gives that file precedence over `package-lock.json`; its presence is explicitly unsupported dependency coverage in this version, including when both files exist. Preserve that observation and return incomplete dependency verification, not an expected tree silently derived from shrinkwrap while retaining package-lock as its evidence. A malformed or unreadable competing lock is not permission to fall back. Recheck competing-lock presence at the final observation boundary and on verification, including a shrinkwrap introduced after capture. Archive comparison may still report its own result. Do not add a new resolver or claim shrinkwrap support.

Retain the exact owner-root lock bytes and hash separately from the tarball: npm excludes `package-lock.json` from packages. Support npm lockfile versions 2/3 and ordinary registry package entries, including scoped names, nested/hoisted installations and an explicitly bound top-level npm link. Other package managers and unproven workspace/alias/bundled/override layouts are explicit unsupported coverage, not silently flattened into a PASS.

Use native npm's complete `ls --all --long --json --ignore-scripts` at the installation owner, then select the package by its exact resolved path and compare only its transitive subtree. Do not select by package name alone. A filtered `npm ls assuredloop-base` can omit the dependency subtree; an unfiltered listing from the installed leaf package can falsely report hoisted dependencies missing. Preserve native diagnostics, attributing unrelated sibling errors separately instead of claiming either root-wide success or selected-package failure.

Use npm's separate `ls --package-lock-only --all --long --json --ignore-scripts` as the lock-derived topology only after verifying that the exact retained owner-root package-lock is the effective supported input, not as an installed observation. Preserve the Node/npm versions and effective listing arguments with these observations; exclude inherited filtering that would hide required selected-subtree coverage or report it unsupported. Re-read each selected actual package manifest from its validated realpath and compare name, version and dependency declarations with the native topology/lock-derived expectations. Ordinary `npm ls` can reuse stale hidden-lock metadata: a probe changed a linked dependency's actual manifest from 1.0.0 to 2.0.0 while both normal and lock-only listing still reported 1.0.0. Do not delete or modify a real hidden lock to make validation pass. Missing/mismatched actual manifests or topology that cannot be reconciled are findings, not fresh installed identities.

Lock-derived expected identities must be compared with actually acquired installed identities. The expected tree is not the actual tree. Missing required, mismatched, absent optional/platform-specific, duplicate-path observations and unavailable/unsupported nodes remain distinguishable; optional peers declared through `peerDependenciesMeta` are included in this distinction. Record the lock's declared resolved/integrity values as declarations, not independently measured dependency archive checksums. A missing optional node is not an installed package. Inspect no dependency source code and execute none of its lifecycle scripts. Explicit selection permits npm metadata acquisition at the named installation owner and selected linked source; reject independent manifest reads through unresolved or out-of-scope dependency links and report unsupported coverage rather than reading arbitrary paths from report data.

Verification compares the explicitly selected current lock's bytes with the retained copy and the supported selected dependency identities with their captured/locked identities. Any drift is reported independently of the toolkit archive comparison. Matching names/versions/lock metadata never proves dependency file contents unchanged. This limitation is visible even in a successful result, not hidden in a distant README.

### 5. A small versioned report, not a new workflow authority

Implement one versioned local capture-report JSON Schema alongside the existing schemas, without changing the existing Workflow context or Evidence vocabulary. Reuse shared value constraints where applicable. The record contains:

| Group | Recorded meaning |
| --- | --- |
| Version and operation | Report format version; capture observation, not an approval record |
| Selection | Invoked package realpath/name/version; observed source-root/HEAD/origin or unavailable reason |
| Contract | Verified generated metadata/source and contract check result, separate from code/assets source |
| Artifact | Fixed bundle filename, supplied/generated origin, archive size/SRI/SHA-256, sorted member descriptors |
| Source comparison | Packaged changes versus fixed HEAD, separate general dirty observation and coverage gaps |
| Dependencies | Fixed lock-copy filename/hash/version or unavailable reason; explicit owner-root observation, selected metadata inventory, findings, `content_verified: false` |
| Observation | Start/end times, compared input identities/digests, stable/drifted/incomplete result and declared observation limits |

Checks return per-dimension results and an aggregate `pass`, `invalid`, `incomplete` or `error`. `invalid` means a measured mismatch/unsafe input; `incomplete` means required comparison coverage unavailable/unsupported; `error` means an operation could not complete. Exit 0 requires all declared required comparison dimensions complete and matching; other aggregate states exit 1. Optional Git history is not required for a Git-less installed-package byte check; absent dependency coverage still prevents a full verification PASS. A stable capture can retain an artifact while truthfully returning incomplete dependency/source coverage. Malformed records cannot provide paths or exemptions to bypass checks.

The new JSON file is a versioned tool output contract, not a mandatory committed run artifact. The shared Evidence format may reference a safely published summary or fixed file under existing rules; capture output alone is not a qualifying PR review. Absolute paths, private dependency identities and local source origins are local observations: review/redact before external sharing, and never publish complete private locks by default.

An existing helper's `unavailable` diagnostic maps to incomplete comparison coverage here; an execution failure maps to `error`. Preserve the underlying reason and dimension rather than reinterpret either as a mismatch. Always show supplied/generated archive origin next to an SRI mismatch: it proves different archive bytes, not tampering or unequal installed content. The independently supplied expectation remains a separate input; the tool cannot authenticate how a user obtained it.

### 6. Bounded observation, not atomic or malicious-runtime attestation

Before acquisition, snapshot the resolved package identity, native member inventory/raw hashes, supported lock bytes and selected dependency metadata. Reacquire the same values after packing/reading and immediately before returning. Compare captured archive members to these observations. Re-resolve the executable/package link at the final boundary. Detect persisted changes, additions, deletions, lock/metadata drift and link retargeting; report the differing dimensions without replacing earlier evidence.

Do not promise to detect a change-and-revert between observations or stop subsequent edits. Avoid timing sleeps in tests: an internal injected acquisition boundary may trigger a deterministic fixture mutation; the test still exercises the production comparison. A self-run modified CLI cannot prove it was not modified maliciously. The runtime, native npm executable and OS remain trusted prerequisites; independent review is not replaced.

Capture output must not become one of its own packaged inputs. Reject an output destination inside packaged asset directories, a dependency tree or an existing bundle. A fresh explicitly selected ignored `local-data/` directory is suitable only when native package membership confirms its exclusion; do not infer exclusion solely from `.gitignore`. Recheck inventory after output creation and withhold success if output entered the package. Work scratch is owned, bounded and not published. Never delete or overwrite a preexisting path on failure; report any newly created partial bundle as incomplete.

### 7. Guidance and delivery remain proportionate

Update existing adoption and review Skills, README usage and package help. Explain which command verifies which facts, how to supply the independent expected SRI, how to retain/use a dirty overlay, what a missing lock means, and when a separate adoption decision is needed. Do not add another activity Skill or automatic CI integration for two related helper operations.

This project's owner has chosen the existing linked executable for the current work and `npm link` before that executable in any pipeline. That is an execution choice for this consumer, not a shipped universal policy and not permission for the new helper itself to modify global links.

## Risks / Trade-offs

- Full npm inventories and fixed-HEAD exports cost local I/O. Use them explicitly at adoption/review checkpoints, not on every existing command; report limits instead of partial success.
- Retained report and archive can both be replaced. Verification needs the separately selected expected SRI and an appropriate independent evidence source; neither report shape nor its own digest authenticates the publisher or an owner decision.
- npm layouts and optional packages differ. Bound supported formats, use native metadata and expose unsupported cases; do not create a custom general resolver to conceal gaps.
- Artifact and dependency inputs can change concurrently. Repeated observations catch visible changes but do not provide filesystem atomicity or future stability.
- A newer helper can run while the consumer still binds an older package. Keep actual tool selection and accepted policy/package declarations separate; never silently update the binding to make a diagnostic pass.
