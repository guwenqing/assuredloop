## Why

AI-assisted work needs a clear, traceable path from a rough request to verified delivery without losing the project's current requirements or making humans micromanage execution. Establish this through OpenSpec's native tools and compatible extensions, with GitHub managing work and collaboration rather than a parallel specification or task system.

## What Changes

- **Native reuse:** use OpenSpec to create, inspect, plan, update, validate, synchronize and archive changes. Extend demonstrated gaps through supported configuration and workflows. All authored executable tooling scripts use the Node.js runtime, matching OpenSpec. Do not fork or copy its core, or recreate its existing mechanisms.
- **Reusable tooling, separate consumer data:** scripts, Skills and templates operate from explicit target configuration, parameters and native context, not hardcoded identities or work records of this repo. AssuredLoop Base is itself one consumer. Keep its repository binding and actual planning/delivery data separate from reusable tooling, and verify adoption against a differently named and configured target without modifying tool source.
- **Installable CLI distribution:** deliver the toolkit as a versioned npm package with a CLI and project initialization, comparable to OpenSpec's installation model. Verify the packed artifact and consumer initialization without a source checkout; registry publication itself requires the release identity and publication authorization.
- **Issue-first intake:** accept a rough request as a GitHub Issue. Triage uses Explore to add context, preserve the original request and distinguish confirmed understanding from assumptions. Route work into Task/Bug execution, Epic planning or a bounded Spike.
- **Proportionate paths:** route additions to an ongoing Epic/OpenSpec change to the person or agent responsible for its active plan to assess and update it; accepted additions are handled like tasks from the original breakdown. Later follow-ups reference the original task and relevant delivery or specification context without rewriting archived plans. Implementation-only handling is allowed when the work implements, restores or improves the solution within accepted requirements, constraints and material design decisions; meaning-preserving wording edits do not by themselves require a new Proposal. Ticket size or untouched spec files are not proof: validation gathers the applicable basis and evidence, and independent AI review assesses this boundary. Changes to the accepted agreement return to Proposal review. Epic work receives deeper exploration, a formal OpenSpec change and task decomposition into linked sub-issues. Spike work delivers evidence, conclusions and limitations, including negative or inconclusive findings, then closes as research; a human decides whether to start new formal work from it. It never automatically becomes an implementation request.
- **Oversized requests:** clarity alone does not make a huge Epic ready for delivery planning. Triage should normally route work needing decomposition into several independently scoped requests through a bounded Spike, even when its overall goal is clear. That Spike delivers a decomposition recommendation and then closes; the human decides whether to create the recommended requests. Neither request creation nor implementation starts automatically.
- **Work-category Skills:** every category of work that creates or changes traceable content, including GitHub Issues, repository files and the workflow itself, needs appropriate Skill guidance. Organize Skills around coherent work such as request triage, planning and work decomposition, implementation or follow-up handling; individual edits, links and status updates are steps, not separate Skill requirements. Reuse native OpenSpec Skills where sufficient and add or extend guidance for uncovered work. A script is an execution helper, not a substitute for a Skill: the relevant Skill must explain when and how to use it and interpret its result. Settle the grouping in Spec and Design without a fixed Skill count. Users choose who performs the work; PM, Architect and Developer are examples, not prerequisites. Planning does not authorize business-code edits; implementation needs its own scoped assignment. Producers cannot independently review their own output.
- **Creation guidance and validation agree:** a Skill must guide the actual work, not merely name a category. For example, request triage must explain how to enrich and route an Issue; turning planning into implementation tickets must explain how to create the required task context and associations. The applicable required format, fields, references, statuses and completion evidence must be discoverable through the Skill and its authoritative templates/contracts, together with the applicable checks and how to handle failures or unresolved meaning. Do not hide requirements only inside validator code or require an executor to guess them after producing an invalid artifact. Keep a single rule source through references rather than duplicating every constraint in each Skill. Representative use of the Skills must demonstrate that an executor can create or update conforming artifacts using those instructions, without needing the original conversation.
- **Separate work ownership:** planning/design work and implementation work are distinct, independently assignable Issues, not one ticket that silently changes purpose. Planning work hands off agreed requirements, decisions and context; implementation Issues reference those outputs. Each work item has an identified owner, while users may staff the activities differently. These are work and accountability boundaries, not a prescribed organization chart.
- **Planning and closeout boundaries:** one planning Task covers further exploration, Proposal refinement, Specs, Design, decomposition and handoff, and ends when that outcome has passed review. Developers execute the linked implementation Tasks. A separate closeout Task returns overall validation, current-spec synchronization and archive to the Epic/change owner. Its PR receives the same applicable pre-merge checks and independent review; only successful closeout permits overall completion. Artifact stages and review rounds alone do not justify more Issues.
- **Task and delivery traceability:** connect requests, requirements, design, tickets, PRs and evidence at useful granularity, not just through an Epic's membership. Use GitHub for work collaboration and repo artifacts for formal planning. Avoid duplicate task bodies, manually maintained reverse lists and status changes that require a new formal change. Design must settle the authoritative task/status split and how native task tracking and ticket references work together.
- **Current specification baseline:** integrate change deltas into the current specification set rather than leaving the project understandable only through historical proposals. Archive is historical: later work references relevant current specs and prior work; a new formal change does not rewrite an archived change's plan. A Task/Bug may have no relevant Spec, but review must assess that claim rather than require fabricated links.
- **Mechanical checks and reviewer context:** check required records and formalization are present, structured fields and references are valid, versions and ticket statuses are consistent, and applicable evidence is available. For an Issue closed as completed, missing required evidence or inconsistent status is an error; legitimate research completion or cancellation has different obligations. Gather focused original basis, actual differences, known impacts and open questions for AI review rather than claiming mechanical semantic proof. Independent review judges whether the implementation-only or spec-irrelevance claims are justified and whether actual code, other deliverables and observed behavior satisfy the requirements. Approved text, a checkbox or ticket state is not proof of implementation. Unsupported completion, whether detected mechanically or established by review, cannot qualify parent work.
- **Verification and delivery:** executable work follows independent test authorship, genuine RED/GREEN and relevant controlled-fault checks; non-code work uses appropriate validation. Workers finish internal independent review using the configured Sol/Astra-level policy. This initial change uses native checks and explicitly executed review handoffs with results recorded before submission or merge; it does not implement automated review setup or CI/CD jobs. A separate later Proposal will add automated pre-merge checks and external-review triggering through the selected integration. Review uses native tool outputs and focused original requirement, Issue, change and evidence context, not the producer's conclusion as truth. The change owner resolves findings and obtains required human approval. Missing reports, interrupted agents, pending checks and closed tickets are not completion. Fable is not used unless explicitly requested.
- **Human decisions, AI operation:** by default the user reviews and accepts new or materially changed Proposals before their changes are merged. AI performs implementation, merge and operational follow-through within accepted scope once applicable checks pass; the user need not approve every implementation PR. Deviations return to the affected decision. Further approval-policy flexibility is later work, not an invented classification in this release.
- **Self-use and evolution:** build this extension using native OpenSpec planning and explicitly observed owner/review boundaries. After verification, acceptance and activation, use the resulting workflow for later changes to itself, its Skills, configuration, validators and CI. Demonstrate an actual governed self-change; bootstrap is not a permanent exemption.
- **Bounded refinement:** details and necessary additions can be incorporated while developing this Proposal, but they remain bounded by its agreed outcome. Do not turn refinement into an unbounded larger release. Material expansion returns to the human decision; work outside this outcome remains explicitly deferred for a future Proposal rather than silently entering implementation or being claimed complete.

## Capabilities

### New Capabilities

- `workflow-goals`: A native specification of the already agreed project-wide goals and constraints, giving the L1 writing pilot a shared home; this adds no runtime subsystem or hierarchy engine.
- `work-intake-and-planning`: Request triage, proportionate planning, bounded research and separately owned planning/design and implementation work grounded in native OpenSpec.
- `github-work-traceability`: Issue decomposition, task and requirement references, PR boundaries and evidence-backed work status.
- `specification-baseline`: Integrated current specifications, delta-to-baseline traceability and immutable-by-policy archived planning.
- `review-and-validation`: Test-first work, native checks, explicit independent-review handoffs, focused context, issue-completion assessment and Proposal-level human decisions; automated execution setup is deferred.
- `project-workflow-adoption`: Work-category Skills covering changes to traceable Issues, repo artifacts and workflow rules, with usable creation/update guidance aligned to validation, project-specific policy and compatible extensions, without a mandatory bot topology or database.
- `workflow-self-evolution`: Initial activation and subsequent changes governed by the accepted extension itself.

### Modified Capabilities

None. This is a fresh repository, not a migration of the previous framework.
