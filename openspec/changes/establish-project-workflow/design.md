## Goals / Non-Goals

**Goals:** define an implementable local workflow extension, a compact formal record contract, native-compatible delivery tracking, complete work guidance, useful read-only validation/context tools, and a tested closeout/activation path.

**Non-Goals:** a replacement OpenSpec parser, workflow scheduler, universal requirement ontology, new change-size taxonomy, bot accounts, multi-repo coordination, automatic review provider integration, CI installation, or a mandatory database. This plan does not install its proposed helpers or Skills.

The current delivery boundary is the expanded Proposal at `5c1f33a`, explicitly accepted by Wenqing on 2026-09-07 via AL Architect and [recorded on PR #5](https://github.com/guwenqing/assuredloop-base/pull/5#issuecomment-5576464303). That owner decision, not the producer's assessment of whether packaging was only a detail, authorizes the six delta items relative to `55e73cc`. This revision disposes the independent design review; it is not merge or implementation authorization. New details are assessed against the accepted outcome. Necessary bounded refinements are incorporated with traceable review; material expansion returns to the owner. Deferred automation/CI, multi-repo coordination, bot orchestration and generic hierarchy enforcement remain incomplete follow-up candidates for future Proposals, not hidden Tasks of this change. Registry publication is an explicit release operation requiring confirmed identity and authorization, not a background side effect of producing the package.

## Decisions

### 1. Native artifacts and one readable requirement hierarchy

Use the existing native change, instructions, delta format and sync/archive workflows. Do not patch upstream code or copy its library implementation. The additional `workflow-goals` Spec gives the already agreed L1 goals a normal native home; it is not a seventh runtime subsystem. Each of the six L2 capability Specs references a named L1 goal; its Requirements and Scenarios define L3 behavior. Cross-capability links identify related contracts. Proposal and Design are not themselves L1 and L3.

The mapping is intentionally ordinary Markdown:

| L1 goal | L2 capabilities | L3 examples |
| --- | --- | --- |
| Work is traceable and proportionate | Intake/planning; GitHub traceability | Bounded Spike closure; task basis; planning handoff |
| Shared facts support human and machine judgment | Specification baseline; review/validation | Full-delta synchronization; unavailable evidence; semantic review |
| Reuse supports governed evolution | Workflow adoption; self-evolution | Usable work guidance; activation; governed self-change |

During the active change these paths live under `changes/establish-project-workflow/specs/`; closeout integrates all seven native Specs under `openspec/specs/`. Relative links between capability directories survive that operation. Requirement headings are the native addressing unit; do not introduce layer IDs, copied human-only documents or an automated layer graph. A rule-level link is used where a specific rule is the work's basis; the L2 purpose link does not pretend to prove every lower rule's relevance.

Alternative: keep only L1/L2 labels in every Purpose. Rejected because this scattered the global goal basis. A separate custom goals ledger or ignored README would require a separate synchronization contract; a native Spec uses the existing mechanism. Normal future changes update these goal requirements through deltas like any other Spec.

### 2. Work ownership and Issue boundaries

Use the owner's familiar routes: incoming Request, Epic, Task, Bug and Spike. On this personal GitHub repo these are repository labels, not organization-level native Issue Types. Map the category names in project configuration; do not infer a new approval taxonomy from them.

An incoming Issue retains its original request while triage enriches it and changes the route when justified. An Epic holds the overall delivery scope. Its planning Task covers exploration through reviewed Design, task decomposition and handoff. It can have several PRs and closes at that planning outcome, not at Proposal merge and not after all development. Implementation Tasks and the closeout Task are separate children of the Epic; they reference the planning output. A closed planning Task need not be reopened for routine development. If development reveals a material plan defect, the responsible owner explicitly reopens or revises the appropriate planning work with a reason.

Split work for a meaningful independent result or responsibility. Do not split every artifact, field, test, review round or day into a new Issue. Additional work within an active change returns to its owner; archived deliveries are not edited to register later tickets. Small implementation-only follow-ups use current context and prior delivery references. Huge or unclear requests can produce bounded Spikes, whose conclusion returns to the human without automatic successor creation.

The Epic owner is accountable for the closeout Task; Architect is a staffing example. That owner can have authored the plan, but cannot provide the independent acceptance review of their own closeout PR.

### 3. Native delivery checklist and GitHub operational work

Retain the native `tasks.md` artifact and `- [ ] X.Y ...` syntax. Each checkbox carries stable delivery scope and its verification obligation, and resolves to a GitHub Issue through its own link or an unambiguous work-package heading link. Several bounded checklist steps can belong to one implementation Issue; there is no one-checkbox/one-Issue requirement. The Issue links back to the relevant numbered plan items and specific requirement/design basis, adding operational context rather than duplicating the formal task body.

| Content | Authority | Update point |
| --- | --- | --- |
| Formal scope, requirement/design basis, delivery checklist | Versioned OpenSpec artifacts | Scoped planning or delivery PR |
| Assignment, live progress, questions and findings | GitHub Issue/PR records | Ordinary collaboration updates |
| Checklist completion mark | Delivery snapshot reconciled to evidence | Corresponding delivery/closeout PR |
| Acceptance and executed test/review records | Revision-specific PR/Issue comments | Actual run/review and resolution |
| Final evidence fixity | Versioned closeout `acceptance-manifest.json` | Capture accepted source evidence before archive; never a duplicate work log |

Changing an assignee or posting progress never requires a spec change. An Issue status is not duplicated in a repo status ledger. The native checkbox count remains useful for locating unfulfilled delivery items, but is not an acceptance verdict.

During a PR, checked items mean the candidate contains the claimed contribution, subject to review and merge. The responsible Issue remains open until its applicable delivery is accepted. Checks therefore distinguish candidate contribution from merged delivery. A closeout PR can contain the final checklist mark while its own closeout Issue is still open; that self-reference is not an unsupported closed-child exemption. All prerequisite implementation delivery must already be accepted. After merge the same file is the delivery snapshot, with no extra commit merely to change an operational status.

Checklist deliverables must be achievable before that PR merges. They do not include performing their own merge, post-merge confirmation or Issue/Epic closure. Those operational obligations remain in the GitHub work record and are checked there after merge. The closeout checklist therefore delivers the synchronized/archive candidate and reviewable acceptance package; it does not predeclare successful post-merge follow-through. An archived tasks.md never needs to be rewritten merely to record Issue closure.

Native `apply` reads and updates tasks.md. The delivery Skill adds the GitHub lookup and evidence reconciliation around it; it does not relabel native progress as live GitHub status. Native `list`/archive also read task files, so setting only `apply.tracks: null` would not implement a complete external task provider. Keeping native tracking avoids that fork/adapter project. Where native guidance is broader, project guidance limits execution to the assigned Issue's referenced checklist items.

### 4. Minimal structured relationships, not a second task database

Use human-readable Issue/PR bodies with a single JSON block under `## Workflow context`. Use a small JSON Schema contract for that block, with descriptions and valid examples. JSON keeps parsing unambiguous; prose remains the source of the human request and explanation. Exact schema/example files are implementation outputs, not hidden rules inferred by a validator.

The minimum record vocabulary is:

| Record | Required relationship data | Conditional data |
| --- | --- | --- |
| Incoming Request | No pre-triage block required | Triage adds its route rationale and next work context |
| Routed work Issue | `activity`, `request`, `basis` | `change`, `plan_items`, `depends_on`, `prior_work`, `no_spec_reason`, `split_rationale` |
| Work PR | `issues`, `change` when applicable, `basis` | `plan_items`, `no_spec_reason` |
| Evidence comment | `head`, `scope`, `result`, `evidence` | `producer_session`, `reviewer_session`, `reviewer_model`, `review_depth` for review; `no_head_reason` for non-revisioned research; command and exit result for executed checks |

JSON `activity` is the sole authoritative work-guidance selector. Its values are `adopt`, `triage`, `plan`, `research`, `deliver`, `review`, and `closeout`, corresponding to the seven work rows in decision 7; these are not change-risk types. An Issue implementing adoption tooling uses `deliver`; a work item actually installing it uses `adopt`. Standalone review work can use `review`, while an ordinary review comment uses the evidence schema without requiring another Issue. Rough Requests and container Epics need no selector until executable work is assigned.

Use `type:` labels for the configured Request/Epic/Task/Bug/Spike category. Rename the former `activity:` label namespace to `discipline:`; discipline is optional presentation/assignment context and never selects a Skill or acceptance rule. `repository.labels.discipline` maps activity values to display-label names, defaulting `adopt`/`deliver` to `discipline:development` and `triage`/`plan`/`research`/`review`/`closeout` to `discipline:architecture`. Projects can change or omit that mapping. A missing or mismatched display label is a presentation warning, not a replacement selector. In this handoff #2 is `plan`, #6-#9 are `deliver`, and #10 is `closeout`. Do not duplicate ticket state or assignee in JSON.

For no-Spec work, request context still exists and `no_spec_reason` explains the exemption; an empty list alone is not sufficient. `change` identifies the active native change, not a copied Proposal body. Later work references archived delivery without editing it. For Git-based assessment, `head` is the full commit assessed even when the comment lives on an Issue. Research without a Git-based subject can use explicit `head: null` with required `no_head_reason` and report evidence refs/digests; this exception cannot be used for code, policy or PR acceptance. It does not invent an implementation PR or claim the research report is stored in Git.

Use one structured `RepoRef` shape for `basis`: `{repository, revision, path, anchor?}`. `repository` is a configured `owner/repository` identifier, `revision` is a full commit SHA, `path` is normalized repo-relative POSIX text with no absolute path or `..` segment, and optional `anchor` is the exact Markdown heading slug. `plan_items` uses the same fields except `anchor`, plus a nonempty `items` array of task numbers. The bound repository is required unless `repository.allowed_reference_repositories` explicitly permits another known checkout. Resolve with Git objects at that revision, without checking out or executing candidate files. A missing permitted local object is reported; remote retrieval, when allowed, uses the trusted GitHub adapter, never a URL supplied by a record. Templates render human blob links from valid structured refs; URLs are presentation, not machine authority. Transfer/rename requires an explicit verified binding/alias update, not blind redirect following.

Use qualified `owner/repository#number` strings for Issue references and `depends_on`. Evidence references use `{repository, comment_id}` for a GitHub comment or a `RepoRef` for a versioned file. Creating/reviewing the plan requires referenced work to exist with clear scope; execution/closeout applies prerequisite-delivery checks. These are relationships, not duplicate state. Required shape and consumer alias/allowlist checks are defined in the schema/adapters delivered by package 1, not guessed from rendered URLs.

A task gets its current owner from the GitHub assignment or an explicit named responsibility in its body when a bot account does not exist. Assignment is mutable operational data. The fixture/record schema requires that responsibility be discoverable at handoff; it does not falsely authenticate a model identity.

Schema-required fields depend on the declared work and lifecycle point. A rough incoming request is valid before triage; a planning Task can exist before its future design file exists. At handoff, references to the agreed plan must resolve. A pre-merge candidate can reference files in that PR head. Work closed as delivery requires merged evidence; a cancelled/superseded Issue requires a reason and contributes no delivered scope. Spike completion checks its research obligations, not implementation artifacts. Ambiguous or missing relationships are reported, not filled in by guessed links.

Single-source split: Specs own behavior, JSON Schema owns field/type shape, and Skills/templates reference both. Generate or check template examples against the actual schema. Do not maintain independent copies of mandatory fields in every Skill. Add extensions through documented project configuration and namespaced schema fields; do not make arbitrary unknown fields silently pass as accepted policy.

### 5. Small local tools and explicit trust boundaries

Implement a Node.js ESM CLI using the standard library for filesystem, Git subprocesses and JSON. All executable scripts maintained by this extension, including setup, validation, generation and test helpers, use Node.js; do not add Python or shell-script implementations of the extension. Declarative configuration and documented invocations of native tools are not another runtime. Use native OpenSpec CLI JSON/status/instructions/validation for OpenSpec artifacts, not a new parser. Use `gh api` to fetch GitHub records and native parent/sub-issue relations; paginate and report unavailable input. The only planned additional validation dependency is a pinned direct Ajv 8 version for standard JSON Schema, selected and checked for release age before installation. Do not rely on an undeclared transitive dependency. [Ajv documents schema-based JSON validation](https://ajv.js.org/guide/getting-started.html).

External prerequisites are Node.js compatible with the pinned OpenSpec release (1.12.0 declares Node >=20.19.0), Git, OpenSpec 1.12.0, and GitHub CLI `gh` >=2.88.0 (the validated baseline here). npm does not install or authenticate `gh`. Preflight reports `tool-unavailable` with a reason such as `missing-binary`, `unsupported-version`, `authentication-required`, `insufficient-access`, `rate-limited` (including retry time when known), or `transport-error`. Confirm repository access before treating a resource 404 as `record-unavailable`; ambiguous access is not proof a record is missing. Neither outcome permits a delivery PASS. Help/version and local initialization can work without GitHub access; explicitly local-only diagnostics report skipped GitHub checks and cannot claim pre-merge completion. No auto-login, privilege escalation or automatic `gh` installation occurs.

Proposed surfaces, to be implemented rather than claimed available now:

- `inspect`: produce a focused review packet from a work Issue or PR.
- `check`: validate applicable structured records, links, revision identity, task evidence and status consistency; a closeout mode adds complete-change/baseline coverage.
- `init`: explicitly selected project adoption, with a preview of files/configuration to add or change. No automatic push, GitHub settings change or account setup.

`inspect` and `check` are read-only. They cannot edit labels, close Issues, merge PRs, run commands embedded in a ticket, fetch arbitrary URLs, execute repo code, or silently repair an artifact. GitHub writes stay explicit operations through the relevant Skill and authorized tool. Fetch only the selected repo and explicit permitted reference scope; missing cross-repo access remains a visible limitation. File resolution stays within the selected repo/revision and rejects traversal or external symlink targets.

Use one `.assuredloop/config.json` with distinct `project` policy and `repository` binding sections. Project configuration selects the workflow contracts and optional extensions; repository binding identifies the GitHub repository and local OpenSpec context. No multi-repo service, mirrored authoritative database or fixed bot topology is needed. Inspectable configuration and entry-point help are part of setup acceptance.

The framework and the consumer have separate roots. The selected target root, its configuration and native OpenSpec context determine all consumer work-data lookups. The framework's install directory provides versioned runtime assets and read-only workflow behavior contracts. A missing target binding is an error, never an invitation to use this checkout's remote, user home, Issue numbers or plan. Generic Skills resolve framework rules from the pinned toolkit contract binding and consumer requirements from the target's native OpenSpec context; neither replaces the other. Shipped templates use placeholders such as `{{repository}}` and `{{change}}`, rendered only from explicit validated context. Unresolved placeholders block a handoff artifact. Do not copy this repo's actual configuration, source requests, changes, credentials or activation records into an adopting project.

The pinned framework package exports its delivered workflow Specs as read-only `contracts/` assets, alongside schemas, templates and runtime code. They are generated from the canonical framework Specs at a recorded source revision and checked for equality, not independently authored as another specification set. Package metadata identifies that version/source revision and the contract paths; `project.workflow` in the target configuration pins that package and any explicit locally governed policy extensions. Installed Skills can read these assets without requiring the original source checkout. Never insert framework contracts into the consumer's `openspec/specs/`, which remains the consumer's own product baseline. Human-readable provenance links in contracts are history, not target routing defaults.

For initial self-adoption before this first change is archived, activation may explicitly bind a package of the already reviewed active-change contract revision. Its metadata declares this bootstrap basis and does not pretend it came from a delivered baseline. Final closeout replaces that bootstrap binding with the integrated, accepted contract release. Later adopters receive the completed package, not this bootstrap project's Issues or activation record. The cross-target fixture must work without the original source checkout and must prove framework rules and consumer requirements resolve from their separate bindings.

Implementation layout (proposed files, not existing implementation):

| Location | Ownership |

| `src/` | Reusable Node.js CLI, native-tool adapters, checks and template/setup helpers |

Distribute through a normal versioned npm package with a `bin` entry, an explicit package-files allowlist and the assets above. npm installs the runtime into its package location (global, one-shot execution cache or pinned project dependency); `init` generates only target-specific configuration and Skill discovery files after a preview. It does not copy the source repository or inject framework Specs into consumer Specs. Preserve native/user-owned files and fail on unapproved conflicts. Running a toolkit version that disagrees with the target's pin requires an explicit compatible selection or upgrade, not silent rebinding.

The binary is `assuredloop`; public npm name/scope remains a release choice. `repository.tools` records selected native tool IDs, not hardcoded destination paths. Resolve each installed tool's `skillsDir` from the pinned OpenSpec tool registry through one version-checked adapter. In 1.12.0 the observed registry is `AI_TOOLS` in the installed package's `dist/core/config.js`; this is not assumed to be a stable public API. Unsupported registry shape/version produces an explicit compatibility error, not a copied forty-tool table or guessed root. Codex `.agents` and Claude `.claude` are this consumer's resolved values; a Cursor/Gemini fixture must use its different native root without source edits. Read and honor `.openspec-target` when roots are shared, never write that upstream marker, and stop on unresolved co-tenancy conflicts. Write only `assuredloop-*` discovery directories and explicitly agreed instruction stubs; preserve upstream/user Skills and files.

Use [npm's bin/package metadata](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#bin) and [npm pack](https://docs.npmjs.com/cli/v11/commands/npm-pack/) rather than a custom package manager. The package allowlist includes runtime, schemas, parameterized templates, reusable Skill sources and generated contract assets, but excludes this consumer's config, active/archived change history, credentials, test-run logs and local work. Test the actual tarball installation and CLI from a different directory without the source checkout. The package name/scope and registry account are release settings to confirm before actual publication; this plan authorizes building/testing the distributable, not registry writes or access changes. Existing `private: true` is not removed merely to make a planning check pass.

A small root README points to usage and the formal Specs; it is not another copy of requirements. This repo's self-adoption uses the same installation/init path as a different target, without a hardcoded self-hosting mode. A cross-target fixture changes repository identity, directory, Issue numbers and label mapping and verifies correct context, links and unchanged source assets.

#### Accepted policy basis and activation record

The effective pointer is the committed `.assuredloop/activation.json`, with required shape `{schema_version: 1, state, policy_ref, contract_package, activated_at, authorized_by, evidence}`. `state` is `active` or `suspended`; `policy_ref` is a structured RepoRef pointing to the accepted formal policy source at a fixed revision. Consumer choices such as `project.review` come from `.assuredloop/config.json` at the trusted current base, not from another unspecified policy-config location. `contract_package` contains `{name, version, integrity, source_ref, contracts_path}`; `source_ref` is the canonical contract RepoRef (its path can be a directory), and `integrity` is the package content-integrity value. `authorized_by` identifies the declared owner and `evidence` contains structured evidence refs for the authorization/review. Timestamps are UTC. Schema validation checks declarations and references; it does not independently authenticate the human decision.

For a PR, resolve the bound target repository and current target base-branch SHA from trusted invocation/GitHub metadata, then read activation and `.assuredloop/config.json` from that base using Git objects. Do not use candidate files or an old merge-base to select weaker policy. Record the selected base SHA and activation digest in the report and recheck if the base changes. The activation's fixed policy/package refs determine checks; candidate policy conformance is supplemental. Changes to activation, model policy, schema or exclusions are themselves evaluated under the pre-change base policy. Once such a change is accepted, its updated pointer becomes effective on the base branch, never by self-declaration in its candidate.

When the base has no activation record, `check` requires explicit trusted-caller bootstrap input `{policy_ref, proposal_acceptance}`. `proposal_acceptance` for this project is the owner's PR #5 comment accepting Proposal revision `5c1f33a`; `policy_ref` must name the corrected planning revision accepted at AL Reviewer handoff before implementation starts. It is not inferred from candidate comments or an unreviewed latest HEAD. The authorized owner/coordinator records that fixed bootstrap input in the handoff. Absent or unresolved activation/bootstrap input yields `policy-unavailable`, not a permissive default. Until a reviewed consumer config exists on the base, the new checker also cannot count model-policy-dependent checks as passed; initial package development uses the explicit native/manual bootstrap review boundary, not its own nonexistent checker. Local/offline calls declare their supplied base and cannot claim live-base freshness without a successful remote check.

Task 4 records the first activation file through a reviewed PR after usable-base verification, using that explicit bootstrap basis. Task 5 replaces the bootstrap package/policy binding with the delivered canonical contract/config revision. The current correction task creates neither activation file nor implementation package. Deactivation is an owner-authorized policy transition evaluated under the active base: `suspended` permits diagnostics and explicitly authorized recovery work, not ordinary success with checks disabled.

### 6. Focused context and two kinds of review

The packet contains the source request, work record, applicable Proposal/Spec/Design fragments, candidate diff, resolved references, task mappings, test/review evidence, known impacted contracts and open questions. It records base/head revisions and fetched mutable Issue/PR records with retrieval time. Distinguish an item not inlined from an item unavailable: neither is silently removed from the reference inventory.

Roots (depth 0) are explicit basis refs, changed-file refs and required work/evidence records. Inline these and directly referenced requirement/decision fragments through depth 1, ordered deterministically by root order then normalized reference. Items beyond depth 1 are listed by structured reference without content. `project.review.context.max_inline_bytes` is a positive integer, default 65536 UTF-8 bytes per serialized response page, including metadata. Content exceeding the page budget is listed with reason `over-budget` rather than cut silently; large reference indexes are paginated with stable counts/cursors. Metadata that cannot fit yields `packet-limit`, not a false complete result. Depth and budget describe presentation, not relevance or acceptance.

Each page/index identifies every discovered item's ref, depth and disposition (`inlined`, `outside-depth`, `over-budget`, `out-of-scope`, `unavailable`), plus counts of pending pages/references. An explicit expansion reads a listed permitted ref in subsequent bounded pages. Out-of-scope access requires an authorized binding change, not an arbitrary URL; unavailable inputs stay unavailable. A reviewer must resolve needed non-inlined context before concluding coverage. For closeout all accepted deltas/delivery records are roots, so nothing vanishes merely because the packet spans pages. For planning, compare Proposal commitments to Specs and Specs to Design/tasks for missing coverage and unsupported additions; implementation review compares actual behavior to its basis. No Top-N relevance cutoff decides what exists.

Mechanical success proves formal checks succeeded, not that a rationale is valid or a feature works. Review evidence requires nonempty `producer_session` and `reviewer_session`; equal declarations or either missing declaration produce `review-independence-invalid`. Different declarations prove only declared distinctness. A false declaration requires independent/human scrutiny and is not authenticated by comparing strings. Include same-session, missing-session and distinct-session controlled faults. Independent review uses a separate read-only agent/session and original evidence. Future external bots/pipelines can consume the same packet; none are installed here.

`project.review` in the accepted config defines the review obligation. `depth` currently has one supported value, `full-scope`: read the assigned scope's original basis and actual changes, assess completeness/correctness/coherence, relevant negative cases and cross-contract impacts, and report inspected scope, unresolved references and findings. It is not a vendor/model strength tier. `internal.allowed_models` is a nonempty array of exact consumer-selected model identifiers; `excluded_models` is an array of identifiers forbidden unless an owner override names the specific review/model and evidence. Exclusion wins over eligibility. Optional `model_aliases` maps private labels to exact identifiers; aliases must resolve unambiguously before use, with both alias and resolved identity checked for exclusion. Missing config or unresolved eligibility yields `review-policy-unavailable`, not a guessed model choice. Evidence declares `reviewer_model` and `review_depth`; checks verify the configured identity/depth declaration, while semantic review assesses whether the work actually met that depth.

The earlier labels Sol/Astra referred to this owner's desired internal models, and Fable to an owner-excluded model label. They were not defined review levels. Consumer setup records the actual available selectors and exclusions in the fields above; reusable requirements do not hardcode those private names. Explicitly owner-arranged external review is a separate acceptance perspective, not required to belong to the worker's internal model allowlist, but it still follows declared independence, full-scope evidence and applicable exclusions/overrides.

Working results remain revision-specific comments. Closeout captures a small versioned fixity manifest as defined in decision 8; full logs and conversations stay external. If head changes materially, obtain renewed review. Re-fetch mutable Issues and compare captured basis before merge; material context drift invalidates the relevant conclusion even if code head did not change. Missing reports and unresolved findings prevent completion. AI owners perform allowed merges only when these obligations and required human Proposal decisions are met.

### 7. Skills explain complete work, with native operations inside

The following are initial work groupings, not a permanent count or role chart:

| Work guidance | End-to-end responsibility | Native reuse |
| --- | --- | --- |
| Adopt the workflow | Inspect target repo; agree configuration; install without overwriting unrelated work; verify usable guidance | Native init/status and generated integrations |
| Triage a request | Preserve request; explore; own the route decision, including implementation-only follow-ups outside an active change; record boundary and no-Spec rationale for review | Explore |
| Plan and decompose | Deepen understanding; Proposal/Specs/Design; create scoped tasks; review and hand off | Propose/instructions; update-change coherence workflow |
| Research a Spike | Bound questions; gather evidence; report limits; close research to human | Explore where appropriate |
| Deliver assigned work | Resolve basis, verify the follow-up/no-Spec claim and return disagreements to triage/planning; test first; implement; review/PR findings; authorized delivery | Apply for a linked active plan; existing-context work without an active change does not fabricate one |
| Review work | Read-only assessment of original basis and actual artifacts; report findings with revision/scope | Native validate; artifact coherence guidance; native verify where applicable to implementation |
| Close a change | Aggregate acceptance; synchronize and verify Specs; closeout PR; archive and completion | Sync-specs and archive-change |

Each explains required inputs, record meanings, decisions, allowed edits, expected outputs, references, checks, failure handling and handoff. The corresponding selectors are `adopt`, `triage`, `plan`, `research`, `deliver`, `review`, `closeout`. Issue splitting is a convention inside planning work, not another Skill. Keep the authored packaged Skill source independent of generated target copies; resolve tool destinations as specified in decision 5, including ownership-marker handling. Deliver root usage/agent instruction entry points as small pointers to the resolved work Skills and native context, not duplicate rulebooks. Repo-specific context is resolved at use time. Triage/development/review trials explicitly include an implementation-only follow-up with no active change, a legitimate no-Spec case and an unjustified exemption.

No Skill promises that invocation alone enforces behavior. Representative execution by an agent without this conversation verifies that the guidance is sufficient. Both guidance and checker defects can be found; do not blame the executor for a requirement hidden only in code.

### 8. Closeout is a normal reviewed delivery

The parent owner schedules a separate closeout Task with explicit prerequisite implementation Issues. A closed developer ticket is an input to validation, not proof by itself. The owner checks the accepted requirement set against integrated implementation and its evidence; unresolved failures return to the responsible work, and material scope changes return to planning/human decisions.

For this release, current Specs mean the integrated contract of completed changes. Pending accepted targets remain in active deltas. Closeout uses a normal branch and PR; no special worktree is required. In the closeout candidate:

1. Read the accepted delta set, latest base Specs and all prerequisite delivery records at explicit revisions.
2. Run native checks and the aggregate delivery assessment; record gaps before synchronizing.
3. Use native sync guidance to apply all intended adds, modifications, removals and renames to current Specs, preserving unaffected contracts and links. Do not just copy delta files with operation headings into the baseline.
   When a requirement heading changes, identify and repair affected current inbound anchors and record the old/new mapping for review. Preserve immutable historical refs; report unavailable historical evidence instead of rewriting archives or following an unrelated redirected repository.
4. Run native current-Spec validation and inspect the baseline diff against every delta. Mechanical checks report coverage/shape and unresolved references; independent AI review checks the actual meaning and preservation of unaffected behavior.

### 10. Bootstrap activation and real self-use

Separate three milestones: reviewed usable base, explicit activation of that fixed revision, and final minimum acceptance after a real governed self-change. Activation writes the versioned file defined in decision 5, with GitHub evidence refs; a mutable comment is not the policy pointer. While this change remains active, that file can reference its explicitly reviewed contract revision. Missing current Specs never means unrestricted policy. This bootstrap did not require a decomposition Spike: its five delivery packages contribute to one owner-accepted workflow outcome, rather than several independently scoped requests; no research completion is being invented.

After base verification, the owner authorizes activation. At the end of the initial guidance trials, and before declaring package 4 complete, record a self-change decision. Prefer a genuine bounded improvement with its own scoped Issue/PR. If none was found, the owner chooses either (a) a concrete deferred follow-up, scoped through the normal Proposal boundary if needed, or (b) a named alternative governed self-change, such as the owner-led closeout PR under the active policy, with explicit reasons and independent review. Do not automatically waive the demonstration or invent a cosmetic issue. If neither is accepted, record a blocked/not-accepted release outcome and return to the owner; do not keep an unbounded silent wait loop or claim completion.

The decision is an evidence comment on the integration/activation work Issue (here #9), using `{selection, work, rationale, authorized_by, evidence}`. `selection` is `improvement`, `closeout-alternative` or `not-accepted`; `work` names the selected qualified Issue reference, or is null for not-accepted. `evidence` includes the owner decision and independent assessment refs. The closeout Issue references this comment; its final manifest captures the decision's summary/digest. Presence of the envelope is mechanically checkable, while suitability of the selected work remains an independent/human judgment.

Activation and self-change remain distinct. For a selected improvement, package 4 verifies its separate delivery before closing; it does not implement it inside the activation checkbox. For an owner-approved closeout alternative, package 4 closes only its reviewed decision/handoff scope and transfers demonstration verification to package 5. It does not claim the demonstration already passed. The final closeout assessment must independently verify the named alternative was actually executed under the active policy before Epic acceptance. This explicit conditional handoff avoids requiring the closeout Task to be complete before it can start. No placeholder successor is created just to satisfy a count.

The separate closeout Task runs after package 4's applicable delivery or alternative-decision handoff. It verifies any delegated demonstration, synchronizes the final delta and completes the reviewed archive. Later work reads the integrated current Specs and trusted base activation/configuration. Neither a candidate validator nor a proposed Skill can exempt itself from current obligations.

## Risks / Trade-offs

- Explicit local execution is bypassable without enforced CI -> make that limitation visible; require actual evidence and review now, with enforcement a separate accepted change.
- GitHub records can mutate or disappear -> retain final summary/digests in the versioned acceptance manifest, re-fetch before completion, and report drift or unavailability; a digest cannot recreate a deleted report.
- Repository identity can change -> verify explicit binding/alias updates against the target's repository identity; never silently follow arbitrary record URLs or reuse an unrelated redirected repository.
- Native checkboxes can be mistaken for live status -> Skills and checks distinguish candidate/merged delivery snapshots from Issue state and actual acceptance.
- Main Specs lag ongoing accepted targets -> active changes remain the explicit pending target context; no claim that the baseline describes uncompleted work.
- Reviewer context selection can omit an impact -> expose exclusions, follow references, and allow expansion; semantic coverage is not mechanically proven.
- Adoption can overwrite user customization -> preview changes, preserve unrelated files, and stop on overlapping unowned content; do not patch global instructions implicitly.
- New record fields can become busywork -> require only data used by a named check or handoff; use Schema descriptions/examples and verify fresh-agent usability.
