## 1. Project adoption and record contracts

Work Issue: [#6](https://github.com/guwenqing/assuredloop-base/issues/6). Package: project configuration, record schema, npm distribution and safe initialization. Basis: [adoption](specs/project-workflow-adoption/spec.md), [traceability](specs/github-work-traceability/spec.md), [Design decisions 4-5](design.md#4-minimal-structured-relationships-not-a-second-task-database).

- [ ] 1.1 Define the minimal JSON Schema, descriptions and valid/invalid examples for configuration and workflow records; verify independently authored schema tests reject missing/invalid required data and accept rough pre-triage requests, staged planning, legitimate no-Spec work and extensible project policy.
- [ ] 1.2 Implement Node.js-only safe local setup and project/repository configuration using native OpenSpec initialization; verify genuine RED/GREEN functional tests for explicit target selection, idempotent adoption, unrelated-file preservation, overlap failure and missing-binding errors, with pinned direct dependencies and no remote writes.
- [ ] 1.3 Deliver versioned read-only framework contract assets and parameterized adoption guidance; verify a fresh executor can configure a distinct consumer fixture without the original source checkout, resolve framework rules separately from consumer Specs, and vary repository identity, path, Issue numbers and labels without source changes or data leakage, with independent review/adoption evidence on the work PR.
- [ ] 1.4 Provide the npm CLI entry and explicit package-files allowlist; verify the actual packed artifact installs and runs initialization/help/inspection entry points without the source checkout, excludes consumer data and logs, and detects incompatible version bindings without performing a registry publication.

## 5. Owner-led closeout

Work Issue: [#10](https://github.com/guwenqing/assuredloop-base/issues/10). Package: final aggregate acceptance, native synchronization/archive and overall completion, owned by the Epic/change owner rather than an implementation worker accepting their own output. Depends on packages 1-4 and any accepted self-use improvement being delivered. Basis: [closeout contract](specs/specification-baseline/spec.md#requirement-owner-led-closeout-verifies-the-integrated-specification), [evidence-backed completion](specs/github-work-traceability/spec.md#requirement-completion-requires-the-right-kind-of-evidence), [Design decision 8](design.md#8-closeout-is-a-normal-reviewed-delivery).

- [ ] 5.1 Assess the integrated outcome against all accepted requirements and delivery records, returning unresolved defects to responsible work; prepare a normal closeout PR that synchronizes all native delta Specs, preserves unaffected behavior and links, and stages archive only after successful native validation and synchronization comparison.
- [ ] 5.2 Regenerate this framework release's packaged contracts from the synchronized canonical Specs, verify exact content and source/version metadata, and replace the self-adoption bootstrap binding with the delivered contract package; verify packed-artifact installation resolves those contracts without the former active-change path or source checkout and keeps consumer Specs separate.
- [ ] 5.3 Prepare the revision-specific aggregate acceptance package and closeout handoff record; verify that the full delta, integrated baseline, prerequisite delivery and current checks are available for independent review, and that the GitHub closeout Issue explicitly retains the required pre-merge review, authorized merge, post-merge confirmation and Issue/Epic closure obligations without marking those future operations complete in this checklist.
