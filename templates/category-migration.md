# Migrate work categories

Use this procedure only for an explicitly authorized consumer migration after the compatible implementation/package has been accepted. Resolve the consumer and selected package as described in the package README. Read contracts/project-workflow-adoption/spec.md and contracts/github-work-traceability/spec.md for the governing migration and category requirements, and schemas/workflow.schema.json for record fields. This is a manual procedure, not an automatic migration command or policy acceptance.

1. Prepare the consumer configuration candidate: remove `repository.labels.discipline`, supply all six distinct category mappings, and bind the actual replacement package integrity and generated contract source. Validate the candidate and review the affected adoption/discovery updates. Keep an unaccepted candidate separate from active configuration.
2. Immediately before remote changes, capture the full current label and Issue inventory, including open and closed Issues. Preserve each affected Issue's identity, body, state/state_reason, assignees, parent/sub-Issue membership, dependencies, category labels and evidence links. Compare with the reviewed migration scope; reconcile newly affected Issues from their actual work, or return an unresolved classification to the responsible owner.
3. Establish the configured Architecture Task label if missing. Reclassify formal planning and aggregate closeout as Architecture Task; retain ordinary implementation/adoption/review Tasks, Bugs and research Spikes under the category/activity contract in templates/README.md. Preserve unrelated labels. A change of assignee or document-only implementation does not justify Architecture Task classification.
4. Check the current Workflow context before replacing each category. When the authorized scope includes repairing a cancelled planning record, preserve its cancellation and original prose/evidence and append only a truthful minimal context: `activity: plan`, its real Request and a resolvable historical Proposal basis. Do not invent plan items, delivered work or retroactive acceptance. An unresolved required fact means migration is incomplete.
5. Apply the reviewed category replacements and remove obsolete discipline labels from the affected Issues. Re-read the records and verify exactly one appropriate category, compatible context and preservation of the captured state, ownership, relations, body and evidence, except for separately identified authorized current-work updates. Relabeling is not delivery credit and does not reopen cancelled work.
6. Only after replacement checks pass, delete the explicitly scoped obsolete repository labels. For a migration from the former defaults, these are `discipline:architecture` and `discipline:development`; do not infer authority to delete other labels from their names. Re-inventory all Issues and labels to verify replacements and absence of the removed labels.
7. Record before/after evidence, actual commands/results, preserved fields, intentional context changes and unresolved discrepancies in the corresponding GitHub Issue/PR comments. Code delivery alone does not prove remote migration completion. Refresh affected consumer package/configuration and adoption evidence before its separate acceptance/activation decisions.

Read-only `init` preview, `check` and `inspect` remain read-only. Initialization does not overwrite an existing conflicting configuration or rewrite historical Git revisions/review records. Update an existing consumer only through its authorized reviewed change. Audit old references by distinguishing removed operational behavior from intentional migration instructions, rejection tests, historical evidence and ordinary prose; a zero-match search is not the objective.
